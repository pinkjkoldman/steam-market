# CR-004 数据库设计与迁移结论（G2）

## 1. 结论

无需 SQL schema 迁移。CR-004 复用现有 `settings` 表中 `app_settings` JSON 行，只增加向后兼容字段 `startupIdentityMode`。

## 2. 物理存储

```text
settings
└── key = app_settings
    value_json.startupIdentityMode = ask | guest
```

不新增表、列、索引、触发器和外键。不在 `steam_accounts`、`sync_jobs` 或日志表中写入 Cookie、会话令牌和认证恢复标记。

## 3. 读写策略

读取：

1. 读取现有 `app_settings`；
2. 字段不存在或值非法时使用 `ask`；
3. 保留 JSON 中应用认识的其他设置；
4. 解析失败时沿用现有安全默认并记录稳定错误码。

写入：

1. 通过现有 `SettingsService` 单路径写入；
2. 使用现有事务/原子替换行为；
3. 不因账户状态变化频繁写盘，只在用户修改“下次直接游客进入”时写入。

## 4. 升级与回滚

升级：旧版本数据天然缺少字段，自动视为 `ask`，没有数据搬迁和锁表窗口。

回滚：旧版本忽略未知 JSON 字段；若旧序列化器重写整行，该字段可能被移除，升级回来仍安全回退 `ask`。

## 5. 一致性

- 设置写入与身份切换不组成跨资源事务；即使设置写入失败，本次仍可进入游客态，但下次恢复 `ask`；
- 身份状态只在内存更新，不允许从数据库“修复”当前认证；
- 本地缓存数据与身份解绑，注销不会破坏用户关注列表。

## 6. 验证用例

- 无字段、`ask`、`guest`、未知值、错误类型和损坏 JSON；
- 写入 `guest` 后重启进入游客，但不出现认证态；
- 从新版回滚后设置可读；
- 注销和会话失效不产生数据库身份写入；
- 数据库只读或写失败时仍可选择游客。
